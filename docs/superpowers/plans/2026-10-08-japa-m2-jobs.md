# japa Milestone 2: Jobs and Worker Profiles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The CoS can delegate work. It starts background jobs that run as worker conversations configured from worker profiles, steers and stops them, and lists them. Each job reports back into the CoS thread exactly once per state change, including across restarts. `japa chat` shows a live job board.

**Architecture:** This builds on M1's kernel (`src/kernel/boot.ts`).
- **A job** is a child conversation owned by a background anchor task. The root document `japa.jobs` tracks it.
- **Messages:** each message to a job (the brief, a steer, a follow-up) is delivered by a durable background `japa.job-run` task. The task submits the message, waits for the run to settle, decides the job's new status in one commit, and posts a report into the root with `requestId report:<jobId>:<seq>`. This follows Pi Durable's `23-subagent-background` example.
- **Worker profiles** are Markdown files with frontmatter. A profile selects the model, thinking level, environment, cwd, built-in tools and extension tools.
- **Workers cannot start jobs:** a job conversation selects an explicit extension list that never includes the CoS's extensions.

**Tech Stack:** M1 stack, with no new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-07-japa-design.md`, covering §5.3 (job tool selection), §6, the job-board part of §7.2 (item 5: non-terminal jobs only, since "finished since last reset" needs M3's reset), the environment dispatch in §4.2, and the gateway's job board from §11.1.

**Pi Durable reference:** the background-subagent example, full source at `https://raw.githubusercontent.com/earendil-works/pi/main/packages/durable/test/examples/23-subagent-background.ts`. Fetch it with `curl -sfL <url>`. Also `node_modules/@earendil-works/pi-durable/README.md`, in particular "Abort and Subagents", "Per-Conversation Agent", "Your Own State" and "Settings".

## Global Constraints

- All M1 global constraints apply: Node 24 erasable TypeScript, `.ts` imports, no new dependencies, `BACKGROUND_CONTEXT`, tests use the faux provider, and code is simple, minimal and readable.
- **Prime directive from the user:** don't overcomplicate. Write minimal code and no code for its own sake. Don't add branches for impossible cases or speculative options.
- Job IDs are decimal strings `"1"`, `"2"`, … from a counter in `japa.jobs`.
- Job status values are `"queued" | "running" | "needs_input" | "done" | "failed" | "cancelled"`.
- The report content format is `[job <id> "<title>" <status>] <text>`. Its requestId is `report:<jobId>:<seq>`, where `seq` is a per-job counter that is incremented in the same commit that decides the report.
- The root conversation's extension selection stays the host default. Set the harness `settings.extensions` to `[japa-cos, japa-jobs, ...extension-built Pi Durable extensions]`. The `japa-worker` extension and `CodingTools` are installed in the registry but never selected by the root.

## Review Focus

1. **Restart mid-job.** After the daemon restarts while a job is working, the job still finishes. The CoS gets exactly one report and the worker gets the brief exactly once. Test in Task 4.
2. **Concurrency.** Never more than `jobs.maxConcurrent` jobs start from the queue. Queued jobs start in creation order as slots free up. Test in Task 5.
3. **Role boundary.**
   - The root never offers `write`, `edit`, `bash`, `job_progress` or `job_complete`.
   - A job never offers `job_start` or any other CoS job tool.
   - A job's environment is the profile's environment and is not read-only.
   - Tests in Task 3.
4. **Stopped jobs stay quiet.** A stopped job never posts a report. Test in Task 5.
5. **Bad worker profile.** A profile with bad frontmatter, an unknown built-in tool, an unknown extension or an unknown environment is skipped and listed in `status().errors`. Other profiles still load. Tests in Tasks 1 and 3.

### Task 1: Frontmatter, worker profiles, settings

**Files:**
- Create: `src/kernel/frontmatter.ts`, `src/kernel/workers.ts`, `workers/general.md`
- Modify: `src/kernel/settings.ts`
- Test: `test/workers.test.ts`, `test/settings.test.ts`

**Interfaces:**
- `parseFrontmatter(text: string): { data: Record<string, FrontmatterValue>; body: string }`.
  - `FrontmatterValue = string | string[] | Record<string, string>`.
  - The text must start with a `---` line, and the frontmatter ends at the next `---` line.
  - Each frontmatter line is `key: value`. Blank lines are allowed. A ` #` comment is stripped to the end of the line.
  - Value forms: `[a, b]` is a list, `[]` is an empty list, `{ k: v, k2: v2 }` is a map, and anything else is a trimmed scalar string.
  - Anything else throws an `Error` with a short message, such as `line 3: expected "key: value"` or `missing frontmatter`.
  - `body` is the trimmed text after the closing `---`.
  - This parser is all the YAML japa uses; skills reuse it in M4. No other YAML features.
- `WorkerProfile = { name; description; model?: ModelRef; thinking?: string; environment: string /* default "local" */; tools: string[] /* default [] */; extensions?: string[] /* undefined = all */; cwd?: string /* leading ~ expanded */; instructions: string /* body */ }`.
- `loadWorkers(dirs: string[]): { profiles: Map<string, WorkerProfile>; errors: { name: string; error: string }[] }`.
  - Reads `<dir>/*.md` in each dir. Later dirs replace earlier ones by profile name. A missing dir is skipped.
  - Required fields: `name` (kebab-case, as for extensions) and `description`.
  - `model` must be a map with `provider` and `modelId`. `tools`, `extensions` and `skills` must be lists. `skills` is accepted and ignored until M4.
  - Any problem gives an error `{ name: "worker:<file name>", error: <message> }`, and the profile is skipped.
- `workers/general.md`: `name: general`, a one-line description (general-purpose background work using the read tool and all extension tools), `tools: [read]`, and a short body of instructions.
- Settings changes:
  - `models.worker?: ModelRef`.
  - `jobs: { maxConcurrent: number }`, default `{ maxConcurrent: 4 }`, merged one level deep like `storage` and `secrets`.

- [ ] **Step 1: Write failing tests.**
  - The parser handles scalars, lists, empty lists, maps, comments and the body.
  - Malformed frontmatter throws.
  - `loadWorkers` overrides by name across two dirs.
  - Defaults are applied: `environment` "local", `tools` [], `extensions` undefined.
  - A file with no `description` is reported and skipped while its sibling loads.
  - `cwd: ~/x` expands to the home directory.
  - `{"jobs":{}}` keeps `maxConcurrent: 4`.
- [ ] **Step 2: Run** → FAIL. **Step 3: Implement.** **Step 4: Run** → PASS; `npm test` → PASS.
- [ ] **Step 5: Commit** `feat(kernel): worker profiles`

### Task 2: Job state

**Files:**
- Create: `src/kernel/jobs/state.ts`
- Test: `test/jobs-state.test.ts`

**Interfaces:**
- `Job = { id; title; brief; worker; status: JobStatus; conversationId: ConversationId; progress?: string; result?: string; createdAt: number; updatedAt: number; seq: number; reported: EntryId[] }`.
  - `result` holds the summary for `done`, the question for `needs_input`, and the reason for `failed`.
  - `seq` counts the reports posted.
  - `reported` lists the answer entries already reported, because several messages can end in one answer.
- `JobsDoc = defineDoc<{ nextId: number; jobs: Record<string, Job> }>`:
  - kind `"japa.jobs"`, version 1, conversation scope, `history: "latest"`, `fork: "initial"`.
  - `initial: () => ({ nextId: 1, jobs: {} })`.
  - It lives on the root conversation.
- `JobDoc = defineDoc<{ jobId: string; environment: string }>`, kind `"japa.job"`. It lives on each job's conversation, so the worker tools and the env dispatcher can find their job.
- Pure helpers, with no I/O:
  - `promote(jobs: Record<string, Job>, max: number): Job[]`. Returns the queued jobs to start now, in creation order (by numeric id), so that the number running stays ≤ `max`.
  - `reportText(job: Job, text: string): string` returns `[job <id> "<title>" <status>] <text>`.
  - `board(jobs: Record<string, Job>): string | undefined`. Returns one line per job whose status is `queued`, `running` or `needs_input`, in id order, or `undefined` when there are none.
    - Line format: `- <id> "<title>" <status>`, followed by `: <progress>` while running and `: <result>` while needs_input.
    - Each progress/result text is cut to 120 characters with `…`.

- [ ] **Step 1: Write failing tests:**
  - `promote` with 4 running and 2 queued at max 4 returns none.
  - At max 5 it returns the lower id.
  - With 0 running it returns queued jobs in id order, up to max.
  - `reportText` matches the format.
  - `board` skips terminal jobs and truncates.
- [ ] **Step 2–4:** RED, implement, GREEN.

### Task 3: Start a job, run it, report it

**Files:**
- Create: `src/kernel/jobs/run.ts`, `src/kernel/jobs/cos.ts`, `src/kernel/jobs/worker.ts`
- Modify: `src/kernel/env.ts`, `src/kernel/boot.ts`, `test/helpers.ts` (add `waitFor`)
- Test: `test/jobs.test.ts`, `test/env.test.ts`

**Interfaces:**
- `Anchor` task: `japa.job-anchor`. It finishes at once; the shape is copied from the example. `JobRun` task: `japa.job-run`, input `{ jobId; conversationId; text; mode: "steer" | "followUp" }`. Phases:
  - **`deliver`:**
    1. Submit `{ type: "input", content: text, whenBusy: mode, requestId: "job:<taskId>" }` to the job conversation, then `wait`.
    2. In one commit on the root `JobsDoc`, run `decide`:
       - If the job is `cancelled`, there is no report.
       - If the job is unanswered with reason `aborted`, there is no report.
       - If it is unanswered for any other reason, set `failed` with result = the reason.
       - If it is answered:
         - If the answer is already in `reported`, there is no report.
         - Otherwise push the answer.
         - If the status is `done`, report `job.result`.
         - Otherwise set `needs_input` with result = the answer's text.
    3. In that same commit, when there is a report: `seq++`, `updatedAt = now`, and checkpoint `{ phase: "report", report: { seq, content } }`.
    4. Also in that same commit, start every job that `promote(jobs, settings.jobs.maxConcurrent)` returns. Each started job is set to `running` and gets a `JobRun` with its brief and mode `followUp`.
  - **`report`:** when there is a report, submit it to the root (`whenBusy: "followUp"`, `requestId: "report:<jobId>:<seq>"`). Then finish the task.
  - Both tasks are created with `{ ownership: { kind: "conversation" }, background: true }` from a root context.
- **`jobsExtension({ profiles, settings, extensions })`** returns the Pi Durable extension `"japa-jobs"`.
  - It contains the tasks `[Anchor, JobRun]`, the tool `job_start`, and the section `"jobs"`, which renders `board()` of the root `JobsDoc` and is omitted when undefined.
  - `extensions` is the list of extension-built Pi Durable extensions keyed by japa extension name.
  - **`job_start({ title, brief, worker? })`.** `worker` defaults to `"general"`. The tool's description lists every profile as `name: description`. In one `api.commit`, it:
    1. allocates an id
    2. creates an `Anchor` and a child conversation owned by it
    3. calls `configure(tx, child, agent)`, where `agent` is:
       - `model`: profile.model, else `models.worker`, else `models.cos`
       - `thinkingLevel`: profile.thinking
       - `cwd`: profile.cwd
       - `instructions`: profile.instructions
       - `extensions`: `[japa-worker, CodingTools, ...selected]`. `selected` is the profile's `extensions` mapped to Pi Durable extensions, or all of them when the profile doesn't set `extensions`.
       - `tools`: `{ remove: <built-in tools (read, write, edit, bash) not in profile.tools> }`
    4. writes the child's `JobDoc` `{ jobId, environment: profile.environment }`
    5. adds the job:
       - If `promote` allows it, the job is `running` and gets a `JobRun` with the brief.
       - Otherwise it is `queued`.
  - It replies `Started job <id>.` or `Queued job <id>; it starts when a running job finishes.`
  - An unknown worker gets the reply `Unknown worker "<x>". Workers: <names>.`, and nothing is created.
- **`workerExtension()`** returns `"japa-worker"`, with:
  - a static section `worker`: you are working on a job for the chief of staff; report notable progress with `job_progress`; when finished, call `job_complete` with a short summary; if you need input, end your turn with one clear question.
  - **`job_progress({ note })`** sets `progress` and `updatedAt` of the caller's job. The caller's job is found by reading `JobDoc` on `api.conversationId`.
  - **`job_complete({ summary })`** sets `done` and `result = summary`, and returns `control: { terminate: true }`.
- **Env dispatcher.**
  - It becomes `async (target, context)`.
  - The root gets `readOnly(<default>)`.
  - Any other conversation reads `JobDoc` through `target.read.snapshot(JobDoc, target.conversationId, context)`.
  - It uses that doc's `environment`, or the default when the doc is absent.
  - An unknown environment throws `No environment "<name>" is installed`.
- **Boot.**
  1. Load profiles from `[<packageRoot>/workers, <home>/workers]`.
  2. Validate them against the known environments (after environment activation), the extension names and the built-in tool names. Each failure is pushed to `status().errors` as `worker:<name>`, and the profile is dropped.
  3. Ensure the root `JobsDoc` exists (commit touching it).
  4. Install `jobsExtension`, `workerExtension` and `CodingTools`.
  5. Set `settings.extensions` (see Global Constraints). Make sure the root still gets every extension tool, and that an M1 test still passes.
  6. Because profile validation needs the environments and env activation runs after `Harness.open`, install `japa-jobs` after environment activation and before `harness.resume()`. Pending `JobRun` tasks resume only once their definitions are installed.
- `test/helpers.ts`: `waitFor(fn: () => Promise<boolean> | boolean, timeoutMs = 5000)` polls every 20 ms and throws `waitFor timed out` when time runs out.

**Faux scripting note:** one faux provider serves the root and the job conversations, and its response function receives `{ messages }`. Route each response on message content. For example, a job's first user message is the brief, and the root sees `[job …]` reports. A shared helper in `test/jobs.test.ts` is fine.

  - **Lifecycle:**
    1. The root calls `job_start({ title: "Sum", brief: "Add 2 and 2" })`.
    2. The job calls `job_progress({ note: "adding" })`, then `job_complete({ summary: "4" })`.
    3. The job ends `done` with result `"4"`.
    4. The root receives exactly one input `[job 1 "Sum" done] 4`.
  - **Tool selection:**

    - A job with a profile `tools: [read, bash]`, `extensions: []` has `read`, `bash`, `job_progress` and `job_complete`. It does not have `write`, `job_start` or the extension tool.
    - Use `(await conversation.agent(ctx)).tools`.
  - **Environment:**

  - **Bad profiles:** a profile naming an unknown tool, extension or environment is listed in `status().errors` as `worker:<name>`, and `job_start` with it replies `Unknown worker`.

**Interfaces:**
- **`job_message({ id, text, mode: "steer" | "followup" })`.**
  - An unknown id gets `No job <id>.`
  - A `queued` job gets `Job <id> hasn't started yet.`
  - A `cancelled` job gets `Job <id> was stopped.`

    1. Set the status to `running` and update `updatedAt`.
    2. Create a `JobRun` with `{ text, mode: steer ? "steer" : "followUp" }`.
  - The reply is `Sent to job <id>.`
  - Messages to existing jobs are not limited by the concurrency cap (ruling: the cap governs starting new work only).

### Task 5: Stop, queue, list, transcript

**Files:**
- Modify: `src/kernel/jobs/cos.ts`
- Test: `test/jobs-control.test.ts`

**Interfaces:**
- **`job_stop({ id })`.**
  - `done`/`failed`/`cancelled` replies `Job <id> already finished.`
  - Otherwise, set `cancelled` in one commit. If the job was `running`, then call `abort` on its conversation.
  - The reply is `Stopped job <id>.`
  - The aborted `JobRun` reports nothing and promotes queued jobs (Task 3 deliver).
- **`job_list()`.** Gives one line per job, in id order: `<id> "<title>" <status>` plus `: <progress or result>`, or `No jobs.`
- **`job_transcript({ id, tail? })`.**
  - Gives the last `tail` messages (default 10) of the job's conversation as text lines.
  - Line formats: `user: …`, `assistant: …`, and `tool <name>: <first 200 chars of result>`.
  - It reads with `api.conversation(id).entries(...)`.
