# japa: password users for the web UI

Status: approved for build. This is an incremental change to the `webui` extension (JAPA-2, see `docs/spec.md`, "japa: `webui`, a browser chat surface", §2.3). The builder folds it into `docs/spec.md`, the README and AGENTS.md.

## 1. Purpose

Today you sign in to the web UI with one generated access token: `~/.japa/secrets/webui.token`, pasted into the sign-in page or opened as `/?token=<token>`. This change removes the token. Instead, you create named **web UI users** with passwords from the CLI and sign in with a username and password.

All users see the same single japa conversation, jobs, status and secret requests. Users are separate logins, not separate workspaces. Nothing else about the web UI changes: the Host and Origin checks, CSP, SSE live stream, API endpoints, theme, transcript and multi-tab behaviour all stay as they are.

`japa setup` is **not** changed by this ticket, because another ticket is reworking setup around the web UI.

## 2. Key technical decisions

### 2.1 Users are managed from the CLI
There is a new command group, `japa webui users <subcommand>`:

| Subcommand | Behaviour |
| --- | --- |
| `add <name> [--password-stdin]` | Creates a user. It asks for the password twice on the terminal (masked, via the existing clack prompter). It refuses a name that already exists. |
| `passwd <name> [--password-stdin]` | Sets a new password for an existing user. This **ends all of that user's sessions**. |
| `remove <name>` | Deletes a user. This **ends all of that user's sessions**. |
| `list` | Prints one line per user: the name and when it was created. It never prints hashes. If there are no users, it prints `no web UI users` and explains how to add one. |

**Password input**
- `--password-stdin` reads the password from the first line of stdin, without confirmation. This is for scripts and tests.
- With no terminal and no `--password-stdin`, `add` and `passwd` fail with a clear message.

**Rules**
- **Names:** 1–32 characters matching `[a-z0-9][a-z0-9._-]*`. Input is lower-cased, so names are case-insensitive.
- **Passwords:** 8–1024 characters. Mismatched confirmations and invalid names or passwords are rejected with a message and exit 1. Unknown names for `passwd` and `remove` are rejected the same way.

**How it runs**
- The command works on the japa home (`$JAPA_HOME` or `~/.japa`) directly. It does **not** need the daemon running.
- The running daemon picks up changes on the next request, with no restart and no reload.
- For Docker instances it works through the existing launcher: `japa --instance <n> webui users add <name>`. The launcher already passes a TTY.
- It appears in `japa`'s usage text and in the README's command table.

### 2.2 Storage
- **Location.** Users live in `<home>/webui/users.json`. The `webui/` directory is mode 700 and the file is mode 600.
- **Kept out of git and jobs.** `webui/` is added to the home's `IGNORED` `.gitignore` lines. That keeps it out of git, and so out of job clones and their sandboxes. The builder must verify that a job can't read it.
- **Record contents.** Each record holds:
  - the name;
  - the creation time;
  - a password hash: Node `crypto.scrypt` with a per-user random 16-byte salt, with the scrypt parameters stored in the record so they can be raised later (at least N=2^15, r=8, p=1);
  - a random per-user **session stamp**, regenerated by `passwd`.
- **Writing.** Writes are atomic (temp file + rename, keeping mode 600). The CLI refuses to modify a file it can't parse; it reports the problem and doesn't overwrite.
- **Reading.** The daemon reads the file when it needs it (sign-in and session checks). It may cache by mtime/size. Hashing and verification use async scrypt, so the event loop is never blocked.
- **Unreadable file.** A missing file means "no users". A malformed file means nobody can sign in, and the status line says so (§2.5).

### 2.3 Sign-in and sessions
- **Sign-in page.** `/login` shows a username field and a password field (`autocomplete="username"` / `"current-password"`) and a Sign in button.
  - When no users exist, the page instead says: no web UI users yet; on the machine running japa, run `japa webui users add <name>`.
- **Sign-in request.** `POST /login` takes the form fields `username` and `password`, with the same 4 KB body limit and Origin check as today.
  - Success sets the session cookie and redirects (303) to `/`.
  - Failure redirects to `/login?error=1`. The page then shows one generic message, "Wrong username or password.", whether the name exists or not.
  - An unknown username is still checked against a dummy scrypt hash, so response timing doesn't reveal which names exist.
- **Throttling.** Failed sign-ins are limited in memory per client address: at most 10 failures per rolling minute. Further `POST /login` requests get 429 until the window passes. A success clears that address's count.
- **The token is gone.**
  - `?token=` is no longer recognised; it is an ordinary query parameter.
  - The `webui.token` secret is no longer declared. A leftover `secrets/webui.token` file is ignored and left untouched. The README says it can be deleted.
- **Session cookie.** It keeps the same name `japa_webui_session` and the same attributes (`HttpOnly; SameSite=Strict; Path=/`). It lasts 30 days and stays stateless.
  - The value is `<name>.<expiry>.<mac>`, where `mac = HMAC-SHA256(sessionKey, "webui-session:<name>:<expiry>:<session stamp>")`.
  - A session is valid only if all of these hold: the user still exists, the expiry is in the future, and the MAC matches with the user's current stamp.
  - So `remove` and `passwd` end that user's sessions immediately. Other users' sessions are unaffected. Sessions survive daemon restarts.
- **Session key.** This is a new generated secret, `webui.session-key` (`generated: true`; at least 32 random bytes, created on first start if unset), read via `KernelContext.secret()`.
  - Changing or deleting it and restarting signs everyone out.
  - Cookies from before this change (the old two-part format) are simply invalid, so the user lands on the sign-in page.
- **Sign out.** A new `POST /logout` (Origin-checked, session required) clears the cookie and redirects to `/login`.
  - The top bar shows the signed-in username and a Sign out control.
  - Sign out only clears that browser's cookie, because sessions are stateless. To end every session of a user, use `passwd` or `remove`.
- **Who is signed in.** The session gate passes the signed-in username to the SvelteKit app (e.g. via `event.locals`), so the app can show it.
- **Unchanged.** Submissions keep the origin `{ surface: "webui", chat: "web" }`. Everything else in the request pipeline (Host check, Origin check, security headers, the 401 JSON for `/api/*` and the redirect to `/login` for pages) is unchanged.

- **README.**

  - The Docker instances paragraph uses `japa --instance <name> webui users add <name>` instead of `cat`-ing the token.
  - The command table lists `japa webui users …`.
  - "Where state lives" lists `webui/users.json` and `secrets/webui.session-key`, and notes that `webui.token` is obsolete.
  - The "Plain HTTP" note talks about passwords instead of the token.
- **`install.sh`.** The Docker install/upgrade message that points at the token file now points at `japa --instance <name> webui users add <name>`.
- **AGENTS.md.** "Running product" is updated: create a user with `scripts/run.sh webui users add <name>`, then sign in.
- **Docs.** `docs/spec.md` (webui §2.3, its acceptance behaviours and implementation notes) and `PROGRESS.md` are updated.

### 2.5 Status line
The `webui` status line (in `japa status` and Telegram `/status`) is one of:
- `http://<bind>:<port> — sign in as a web UI user (N users)`
- `http://<bind>:<port> — no users yet: run japa webui users add <name>`
- `http://<bind>:<port> — can't read <home>/webui/users.json: <reason>`, written with `~` like today.
- `not built — …` and `can't listen on …`, unchanged.

The status line never contains a password, hash, stamp or session key.

### 2.6 Tests
- **CLI.** Tests drive `japa webui users` with `--password-stdin` against a scratch `JAPA_HOME`. They cover add, duplicate, invalid name and password, passwd, remove, list, file modes, and the `.gitignore` entry.
- **Server.** `test/webui-server.test.ts` and `test/webui.test.ts` replace the token tests with:
  - username/password sign-in, including a generic failure for an unknown user versus a wrong password;
  - 429 throttling;
  - `/logout`;
  - session invalidation on passwd and remove, and session survival across restart;
  - `?token=` no longer signing in;
  - the no-users page and status lines.

## Acceptance behaviours

1. **Fresh install.** On a fresh home with a running daemon, `japa status` shows `webui` as `http://127.0.0.1:7337 — no users yet: run japa webui users add <name>`. Opening the web UI shows a sign-in page that says the same. No `secrets/webui.token` is created.
2. **Creating a user.** `japa webui users add alice` asks for a password twice. Mismatched entries are rejected. Afterwards `japa webui users list` shows `alice`, and `japa status` reports 1 user, with no daemon restart. `~/.japa/webui/users.json` has mode 600, contains no plaintext password, and is ignored by git in `~/.japa`.
3. **Signing in.** Entering `alice` and the right password on the sign-in page lands on the chat. The top bar shows `alice`, and reloading keeps you signed in. A wrong password, or an unknown username, shows "Wrong username or password." and stays on the sign-in page.
4. **Throttling.** After 10 failed sign-ins within a minute from one address, the next attempt is refused with 429, even with the right password, until a minute has passed.
5. **Token gone.** Opening `/?token=<anything>` without a session redirects to the sign-in page and doesn't sign you in.
6. **Sign out.** Clicking Sign out returns to the sign-in page. Afterwards `/api/status` gives 401 in that browser.
7. **Password change.** With alice signed in in two browsers and bob in a third, `japa webui users passwd alice` sends both of alice's browsers back to the sign-in page on their next request or reconnect. Bob stays signed in. The new password works and the old one doesn't.
8. **Removing a user.** `japa webui users remove bob` ends bob's session the same way, and bob can no longer sign in. Removing or changing an unknown user exits 1 with a message.
9. **Restart.** Restarting the daemon keeps signed-in users signed in.
10. **Shared conversation.** Two different users signed in at once see the same live conversation and jobs, and a message sent by one appears in the other's tab.
11. **Docker instances.** For a Docker instance, `japa --instance <n> webui users add <name>` creates a user that can sign in at the instance's published web UI URL. The installer's message points to this command.
12. **Scripted use.** `echo 'secret123' | japa webui users add carol --password-stdin` works without a terminal. Without `--password-stdin` and with no terminal, the command fails with a clear message.
13. **Unchanged checks.** The Host and Origin checks behave as before: a foreign `Host` is refused, an IP literal is served, and a POST to `/login` or `/logout` with a foreign `Origin` is refused.
14. **Checks pass.** `npm test`, `npm run typecheck` and `japa check extension webui` pass.
